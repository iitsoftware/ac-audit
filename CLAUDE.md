# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

AC Suite is an EASA-compliant Aviation Compliance Management System with three modules: AC-Audit (audit tracking, compliance management, CAP, 5-Why), AC-Change (Management of Change, task lists, risk analysis, EASA Form 2), and Organization (company/department/personnel management).

## Tech Stack

- **Backend**: Node.js + Express
- **Database**: SQLite via `better-sqlite3` (embedded, single file)
- **Frontend**: Server-rendered EJS templates + vanilla JS
- **PDF**: PDFKit for PDF generation, pdf-lib for LBA template filling
- **CSS**: Custom CSS with auto dark/light mode (blue theme)
- **Single process**: `npm start` runs everything

## Dependencies (9 total)

- `express` — HTTP server + routing
- `better-sqlite3` — synchronous SQLite
- `ejs` — HTML templates
- `uuid` — UUID generation
- `pdfkit` — PDF generation
- `pdf-lib` — PDF template filling (EASA Form 2)
- `xlsx` — Excel file parsing (.xlsx import)
- `adm-zip` — .docx/.zip extraction
- `nodemailer` — SMTP email sending

`audit_plan_line` carries the **two additive columns** the Behördenaudit needed —
`authority_auditor` and `authority_report_date`. Both are additive in the same
sense: an `ALTER TABLE … ADD COLUMN` step in the `planLineMigrations` list of
`migrations.js` next to the column in `schema.sql`, no Datenumschichtung, no
Backfill, and an internal Auditplan never reads either.

`authority_auditor` exists because the Kopfblock separates **three roles that used
to share two columns**: `auditor_team` is the **Behörde**, `authority_auditor` her
**zuständiger Bearbeiter**, `auditee` the QM. `department.authority_name` — the
field `views/organization.ejs` labels "Zuständige Aufsichtsperson Behörde" — is a
*person*, and it used to prefill `auditor_team`, i.e. the Behörde; that
misreading is the reason the column exists, and it now prefills the Auditor while
the Behörde falls back on `'LBA'` (see the Kopfblock pattern). The column arrives
empty, existing rows keep their `auditor_team`, and an internal Auditplan reads
that column as its Auditorenteam and leaves `authority_auditor` blank.

`authority_report_date` is the **date of the Beanstandungsbericht der Behörde** —
the date of her *letter* ("Beanstandungsbericht LBA für Audit Nr. 1 vom
27.7.26"), deliberately **not** the date of the visit. It gets a column of its own
because no existing one can carry it without moving something else: `performed_date`
stands in the `COALESCE(performed_date, audit_end_date, audit_start_date)` of
`authority_date` and would rewrite the Kachel, the Kachelsortierung and the title
of the visit, and `document_rev_date` is the internal "Rev Datum" of a
Themenbereichs-Audit. It is declared **`TEXT` without a default** and therefore
NULL, like every other date of that table: an empty value means "noch nicht
eingetragen" and not an empty string. The column arrives empty and Altbestand
stays untouched — a visit recorded before it simply has no Berichtsdatum, which is
a state and not a gap to be filled from the visit date. In `db.js` it sits in
`LINE_FIELDS`, `createAuditPlanLine`, `updateAuditPlanLine` and
`restoreAuditPlanLine` at exactly the position it holds in `schema.sql` — behind
`authority_auditor`, before `auditee` — so the four read the one order and a
shifted binding cannot creep in.

`audit_checklist_item` carries **two numbers, and they are not interchangeable**:
`sort_order` is the Finding's own laufende `Nr.`, **serverseitig vergeben**
(max+1 on create) and on the Finding screen **display only** — the route still
takes an explicit value, which is what the internal dialog, the two Importwege and
die einmalige Nachvergabe der Altbestands-Nullen beim Laden eines Behördenberichts
send, but no Behörden-Oberfläche writes it by hand —, and `document_ref` is the
**Findingbericht Nr.**, the reference number under which the authority files the
Finding in *its* letter.
Neither is new — both are pre-existing columns the Behördenaudit put to use, so
there is no migration for either (see the two Nummer patterns).

`sms_meeting.department_id` is denormalized on purpose: trash snapshot, PDF header
and audit-log entry all need the department without walking through `safety_year`.
`safety_objective` and `spi_evaluation` carry both `safety_year_id` **and**
`department_id` for the same reason — year-package PDF, trash snapshot, PDF header
and audit-log entry each need the department without a join.

The objective catalogue hangs off the **safety year**, not the department: a new
year copies the previous year's catalogue and the years stay frozen against each
other afterwards. `spi_evaluation` deliberately has **no** UNIQUE index on
(safety_objective_id, safety_year_id) — intervals shorter than 12 months and
re-evaluations produce several evaluations per objective and year. Its
`*_snapshot` columns stay NULL until `decided_at` is set; signing an evaluation
freezes objective wording, target and interval, so a later catalogue edit cannot
rewrite a signed record. `spt` is the printed target text ("Mindestens 20 Stck.");
`spt_direction`/`spt_value` are its machine-readable half, used only to propose a
rating in the frontend. `result_text` is free text because the original CM-006
form carries "Erfüllt", "Nicht erfüllt" and bare numbers like "-2" in that column.

### Checklist Items
- `GET /api/audit-plan-lines/:lineId/checklist-items` — List (with evidence counts and `cap_deadline` — the deadline of the item's CAP item, `''` when there is none)
- `POST /api/audit-plan-lines/:lineId/checklist-items` — Create (optional `cap_deadline` wins over `calcCapDeadline()`; ohne mitgeschicktes `sort_order` = max+1 **innerhalb der Line** über `getMaxChecklistItemSortOrder`, das für eine leere Line `-1` liefert)
- `PUT /api/checklist-items/:id` — Update (replaces the whole row; optional `cap_deadline` overwrites the CAP item's deadline, an omitted one keeps it; ein ausdrücklich gesendetes `sort_order` schreibt durch, ein ausgelassenes behält die gespeicherte Nummer)
- `DELETE /api/checklist-items/:id` — Delete

Die laufende Nummer eines Findings ist damit **vergeben und nicht abgeleitet** —
siehe die Key Patterns zur Findingliste. Nach dem Löschen von Finding 2 bleibt
die Sequenz 1, 3, und das ist gewollt.

Die **Findingbericht Nr.** braucht keine dieser Routen zu ändern: sie wohnt im
vorhandenen `document_ref`, das beide Schreibwege seit jeher aus dem Body
schreiben und `getChecklistItemsByLine` seit jeher ausgibt — **keine Migration,
keine neue Spalte**. Sie steht neben der eigenen `Nr.` und ersetzt sie nicht: die
eine zählt den Bericht dieser App durch, die andere zitiert das Schreiben der
Behörde.

### CAP Items (Corrective Actions)

- `GET /api/departments/:departmentId/cap-items` — List for department

- `POST /api/cap-items/send-email` — Send CAP PDF(s) via email (body: ids[], to, authority?)

### CAP Actions (die n Maßnahmen eines Findings)
- `GET /api/cap-items/:id/actions` — Maßnahmen des CAP-Items, `ORDER BY kind, sort_order, created_at`
- `POST /api/cap-items/:id/actions` — Create (`kind` = `CORRECTIVE` | `PREVENTIVE`, default `CORRECTIVE`; `sort_order` = max+1 **innerhalb der eigenen `kind`-Gruppe** über `getMaxCapActionSortOrder`, das für eine leere Gruppe `-1` liefert)
- `PUT /api/cap-actions/:id` — Update (partiell: ausgelassene Felder behalten ihren Wert, wie `PUT /api/sms-meetings/:id`; ein leerer String bei `target_date` / `completion_date` räumt dagegen auf NULL, dieselbe Konvention wie bei `cap_item.deadline`)
- `DELETE /api/cap-actions/:id` — Delete

Sie hängen am CAP-Item, nicht am `audit_checklist_item`: `cap_item` bleibt der
Speicher alles Korrektiven (siehe Key Patterns), und `ON DELETE CASCADE` räumt
die Maßnahmen mit dem Finding ab. Die vier Routen liegen in
`routes/cap-items.js` neben den Evidence- und 5-Why-Routen: `/api/cap-actions/:id`
ist ein **eigener Pfad** und kollidiert deshalb nicht mit der
Batch-vor-`:id`-Regel von `/api/cap-items/pdf`. Beide Ebenen laden ihren Datensatz
über `loadResource` (`getCapItem` bzw. `getCapAction`), ein fehlender liefert also
wie überall 404, und ein `kind` außerhalb der zwei Werte ist 400 statt einer
stillen dritten Gruppe, welche die Sortierung und die abgeleitete Nummerierung
zerlegen würde. Der Firmen-/Abteilungskontext jeder Log-Zeile kommt aus
`capContext(checklistItemId)` in derselben Datei — der Weg
`checklist_item → line → plan → dept → company`, den auch der Papierkorb-Snapshot
des CAP-Items geht (der ihn seither nicht mehr ein zweites Mal ausschreibt); er
ist best effort und liefert leere Strings statt zu werfen, weil eine halb
gelöschte Kette kein Grund ist, das Schreiben scheitern zu lassen. Der
Maßnahmen-Block des Finding-Screens fährt auf diesen vier Routen (siehe
Key Patterns), und das CM-003-PDF joint dieselben Zeilen als `1. … 2. …` in seine
eine Formularzelle je Art — ohne Zeilen bleibt `cap_item.corrective_action` /
`preventive_action` der Fallback (siehe Key Patterns).

### 5-Why Analysis (internal: L1/L2 only — authority: every Finding)
- `GET /api/cap-items/:id/five-why` — Get 5-Why record
- `PUT /api/cap-items/:id/five-why` — Create/update (syncs root_cause to CAP item)
- `GET /api/cap-items/:id/five-why/pdf` — Eigenständiges CM-002-Formular (file name `Ursachenanalyse_<Audit-Nr.>_<Stufe>.pdf`)

None of the three routes is gated — the boundary lives in the frontend gate on the
CAP level, written down once as `capHasFiveWhy()` in `pdf/cap.js`. Since the CM-003
became the real form it has **no** reader left there either: the sheet has no cell
for a root-cause analysis, `Root cause` is a table column, and the CM-002 is a
document of its own. The Finding level of an authority plan shows the block
unconditionally, and the CM-002 form is a document of its own: a CAP **without** a
`five_why` record yields the empty, hand-fillable form, not a 404 (only a missing
CAP item is one, via `loadResource`). The route loads nothing itself — record,
Abteilung, Firma, Logo and the QM as signer all come out of
`generateFiveWhyPdfBuffer()` (`pdf/five-why.js`), so a later Versand cannot drift
apart from the download.

- `GET /api/audit-plans/:id/pdf` — Audit plan PDF (query: type=open|closed, filter=planned)
- `GET /api/audit-plan-lines/pdf` — Multi-select checklist PDF (query: ids=id1,id2,...)
- `GET /api/audit-plan-lines/:id/pdf` — Single Einzelaudit PDF

- `GET /api/cap-items/:id/five-why/pdf` — CM-002 root-cause form of the same CAP (see 5-Why Analysis above)

Both single-CAP file names come from `capPdfFilename(prefix, cap)` in
`routes/cap-items.js` — CAP report and Ursachenanalyse belong to one record and have
to match on the recipient's desk. Audit-Nr. and Stufe are user input, so the helper
sanitizes both before they reach the `Content-Disposition` header.

## Key Patterns

- Database schema runs on every startup with `CREATE TABLE IF NOT EXISTS`
- SQLite pragmas: `foreign_keys = ON`, `journal_mode = WAL`
- API handlers live in `routes/*.js`, mounted by `server.js`. Each handler: parse request → call db/service → return JSON
- Cross-cutting logic factored into `services/*.js` (email, audit-log, cap-deadlines, trash, backup, notifications, log-cleanup, form2)
- PDF generation lives in `pdf/*.js`: `pdf/common.js` exports `createPdfDoc({ landscape, margin })` + `addPdfFooter()`; domain-specific renderers in `pdf/audit.js`, `pdf/cap.js`, `pdf/risk.js`
- Import parsers live in `imports/*.js` (audit, change, risk) — pure functions that accept a buffer/rows array and return parsed records
- Migrations run on boot: `db.js` calls `runMigrations(db)` from `migrations.js` before preparing statements. The `audit_checklist_item` drop+recreate migration is wrapped in a single `db.transaction()`
- Frontend: EJS template (HTML shell) + vanilla JS (fetch data, render, handle events)
- Page rendering: `renderPage()` helper renders page EJS into layout
- Modals: native `<dialog>` element (`.showModal()` / `.close()`)
- Logo/signature/evidence stored as BLOB in SQLite, served via dedicated endpoints
- Upload pattern: file → base64 in browser → JSON to API → Buffer in DB
- CSS auto dark/light mode via `@media (prefers-color-scheme: dark)`
- CAP status derived from `completion_date` (not stored explicitly)
- CAP items auto-created when checklist evaluation is O/L1/L2/L3, deadline auto-calculated from performed_date + configurable days
- CAP deadline defaults: O=180, L1=5, L2=60, L3=90 days (configurable in settings)
- Notifications: email to department QM when CAP deadline approaches, with repeat option
- Backup: SQLite Online Backup API (async), scheduled with change detection via DB mtime. Path: `BACKUP_PATH` env > DB setting > `$DATA_DIR/backups/`
- Settings stored in `app_setting` table (key-value)
- PDF helpers extracted: `renderAuditLinePdf()`, `renderCapFormPdf()`, `renderRiskAnalysisPdf()`, `addPdfFooter()`
- Multi-select PDF: batch routes registered before `:id` routes (Express route ordering)
- Auth: HMAC-SHA256 session token in HttpOnly cookie, 7-day expiry
- Evaluations: C (Conform), NA (Not Applicable), O (Observation), L1/L2/L3 (Finding levels)
- Audit log: `logAction()` records company_name/department_name context for every action
- Nav toggle buttons: Trash/Log/Config buttons navigate to page on click, back to previous page when active (localStorage breadcrumb)
- Template copy: copies plan structure (subjects/regulations/location only), clears all audit data
- Email helpers extracted: `sendDocumentEmail()` (SMTP config, transporter, replyTo, BCC, sendMail, logAction), `getQmForDepartment()` (finds QM person), `buildAuthoritySalutation()` (formal/informal salutation)
- Authority email: formal letter with salutation, Compliance Monitoring Manager signature, BCC to QM
- Person fields shown in both add and edit dialogs (company: Accountable Manager; department: QM, Abteilungsleiter)
- Trash: DELETE handlers snapshot entity tree (incl. BLOBs as base64) to `trash_item` table before CASCADE delete. Restore re-inserts with original UUIDs in a transaction. Auto-cleanup of expired items (configurable `trash_retention_days`, default 30)
- Docker: `DATA_DIR` env configures DB + backup location (default `/data` in container). Single volume mount for all persistent data
- Share button blink: `has-selection` class on `.select-header` triggers CSS blink animation when checkboxes are selected
- A plan with `plan_type = 'AUTHORITY'` reuses the audit hierarchy with a different reading: the `audit_plan_line` is the **Bericht of one authority visit** (its head block describes that visit — Behörde, Datum, Ort — instead of a Themenbereich, see below), and every single **Finding** is exactly ONE `audit_checklist_item` in a flat list (the whole chain of a visit is written down in the Sprachregelung below). There is no separate table and no new column: `section` is pinned to `'THEORETICAL'` for those rows, with one constant section the existing `ORDER BY section, sort_order, created_at` of `getChecklistItemsByLine` collapses to the order of the report itself. The plan tile, the line list, the CAP items, the evidence files and the trash snapshots stay exactly the tables they are for an internal audit — the whole feature is presentation plus the navigation, labelling, deadline and 5-Why rules below
- **Navigation of a Behördenaudit in one picture** — Abteilung → Kachel → **Bericht des Besuchs** → **Finding**, and nothing else. The plan level and the CAP level, both navigation targets of an internal audit, are skipped: a Behördenaudit has exactly one report, so the plan level would be a list with one row, and the CAP item of a Finding is edited on the Finding itself, so the CAP level would be a second screen for the same record. The four moves that produce it, each detailed in its own pattern below: (1) the tile jumps straight into the report with the `authority_line_id` that `getAuditPlansByDepartment` carries along — a `LEFT JOIN` under a `COUNT(*) = 1` guard, so it stays NULL for internal plans and for an authority Altbestand with 0 or >1 lines, and that NULL *is* the fallback onto the plan level; (2) `POST /api/departments/:departmentId/audit-plans` creates plan **and** report in one transaction, so that id always exists and the `+`-Button of the Zeilenliste becomes superfluous and disappears; (3) `renderCurrentLevel()` knows the segment `{type:'finding'}` and the row click of the Findingliste pushes it instead of opening `#checklist-item-dialog`; (4) the report level shows the Findingliste and **nothing else** — `renderCapSection()` is not called there, and the three things that used to hang on it (ALLE/OPEN/CLOSED filter, Fortschritt, Sammel-Export) sit in that one list. Every one of them is a frontend branch plus a read-only enrichment of an existing statement (`getAuditPlansByDepartment`, `getCapItemsByPlan`) — **no schema change, no migration, no new table and no new column**. Internal audits are untouched in every one of the four: `renderCapSection()`, `renderCapDetailLevel()`, the plan level and the edit dialog all stay exactly where they were, and each branch is guarded on `plan_type` rather than replacing the old path
- The Finding-Screen (`renderFindingLevel()` / `renderFindingDetail()` in `public/companies.js`) carries Stammdaten, Ursachenanalyse (5-Why), Behebungs- und Präventivmaßnahme and Beweismittel on ONE screen — which is a **view onto two rows**, not a new record: Stammdaten save through `PUT /api/checklist-items/:id` into the `audit_checklist_item`, Maßnahmen and Erledigt am through `PUT /api/cap-items/:id` into its `cap_item`, the 5-Why through `PUT /api/cap-items/:id/five-why` and the Nachweise into `cap_evidence_file`. `cap_item` therefore keeps being the storage of everything corrective — CAP-PDF, deadline notifications, the home dashboard and every statistic keep reading exactly the rows they always read; it only disappears from the *surface*, where the LBA sees one Finding and not an audit item plus a corrective action. Both routes **replace** the whole row, which is why each save carries the fields its own screen does not show (`section` and `auditor_comment` on the item — `sort_order` and `document_ref` left that list when the Nr. and the Findingbericht Nr. became fields; `deadline`, `root_cause`, `evidence` on the CAP) unchanged from the loaded object
- The **head block of the report level is the visit, not a Finding** — its children are the Findings. On an authority plan `renderLineDetail()` (`public/companies.js`) therefore draws ONE block headed `Behördenaudit <Datum>` with exactly **six** fields — the **drei Rollen** of `authorityLineDefaults()` plus Datum, Berichtsdatum und Ort: Behörde (`auditor_team`, Default `'LBA'`), Auditor (`authority_auditor`, her zuständiger Bearbeiter), Auditee (`auditee`, der QM der Abteilung), Datum (`audit_end_date`), **Berichtsdatum (`authority_report_date`)**, Ort (`location`). The **Berichtsdatum stands behind the Datum and before the Ort**, and it stands there on **both** surfaces: the Audit-Line-PDF prints the same six rows in the same sequence (see its pattern below), so Blatt und Schirm read one visit in one order. The two dates are not interchangeable and that is exactly why the row is its own: `Datum` is the day the Behörde was in the house, `Berichtsdatum` the day her Beanstandungsbericht is dated — the sheet that goes back to her quotes the latter. Like every other date of this screen it is a `TT.MM.JJJJ` text input through `initDateAutoFormat()` and goes back out as ISO through `parseDateDE()`, so it cannot drift from the Frist and the Datum next to it; the PDF reads the stored ISO value through `formatDateDE()`. **Ohne Berichtsdatum bleibt die Zeile leer** statt einen Platzhalter zu drucken — dieselbe sprechende Leere wie Auditor und Auditee darüber, und `authority_report_date` is NULL until somebody types it. It was three (Behörde / Datum / Ort) until the **Bedeutungskorrektur** of `department.authority_name`: that field is the "Zuständige Aufsichtsperson Behörde", i.e. a *person*, and it had been prefilling `auditor_team`, i.e. the **Behörde** — an Amt printed where a Sachbearbeiterin belonged and no column left for the other one. Separating the two is what `authority_auditor` exists for, and it is why the block grew the Auditor **and** the Auditee row: the three roles an LBA report names are Behörde, ihr Bearbeiter und der Auditierte, and the head block now prints exactly those three. The head block shows exactly what the Anlage prefills — a prefilled column no surface renders would be a prefill and nothing else — and the tile's Unterzeile reads the same `auditor_team` through `authority_auditor_team`, so it prints the Behörde and not a person. The internal `Themenbereich` head (Finding / Vorschriften / Monat geplant) and the rest of the `Audit-Informationen` block (Audit Ort, Dokument Ref., Iss/Rev, Rev Datum, Empfehlung) disappear: they describe a Themenbereichs-Audit, not an authority visit. The heading and the `<h2>` reuse `authorityName()` / `authorityInfoFromLines()` next to `renderAuditPlans()` rather than inventing a second labelling rule, so tile, plan level and this screen print the same date and the same `Behördenaudit (ohne Datum)` when there is none; the heading passes an empty team because the Behörde is a field right underneath it. The `<h2>` had to move off `subject` with it — an authority report is created with `subject = ''` and, without an input for it, would have read `Themenbereich` forever. **Hidden means still sent**: `PUT /api/audit-plan-lines/:id` replaces the whole row, so `saveLineFields()` reads each field through a `fieldVal(id, stored)` that falls back to the loaded `currentLine` when the element is not on screen — internal audits render every element and are therefore byte-identical to before. `authority_auditor` and `authority_report_date` ride that same rule rather than getting an exception for the two columns only this screen shows: the Behördenbericht reads them out of `ld-authority-auditor` and `ld-authority-report-date`, an internal plan hands the stored values straight back, and the server's `b.authority_auditor ?? existing.authority_auditor ?? ''` / `b.authority_report_date ?? existing.authority_report_date ?? ''` stay the guards for callers that are not this screen at all. The one Datum writes `audit_end_date`, because that is the first column the `COALESCE(performed_date, audit_end_date, audit_start_date)` of `authority_date` finds filled (no surface ever writes `performed_date`), so tile, tile order and heading show what was typed; `audit_start_date` stays untouched, which is what keeps a legacy multi-day visit from losing its start. The `<th>` of the plan-level line list follows the same reading and says `Beanstandungsbericht` instead of `Finding` — that level is only the Altbestand fallback (0 or >1 reports), but it lists reports there too
- The checklist of an **authority** plan (`plan_type = 'AUTHORITY'`) renders as ONE flat Findingliste instead of the three sections — heading `Findings`, columns `Nr. | Beschreibung | Findingbericht Nr. | Referenz Paragraph | Level | Frist | Status` (`renderLineDetail()` in `public/companies.js`). The **Beschreibung stands second**, right behind the `Nr.`: it is what a reader recognises a row by, and the two Bezugsnummern behind it are its Fundstelle. Moving it is the whole change and it touches the three parts of that one table together — the `auto` column of the `<colgroup>` travels from fourth place to second (`56px, auto, 130px, 16%, 130px, 100px, 120px` plus the two 56px edge columns), the `<th>` row follows, and the `wrap-cell` class rides along with the `<td>` it belongs to. Because the table is `table-layout: fixed`, those widths **are** the layout and the head has to break inside them: `.checklist-table th { white-space: normal }` (`public/style.css`) overrides the `nowrap` of `.lines-table th`, which had let `FINDINGBERICHT NR.` — wider than its 130px at 12px Versalien — run into the next heading instead of wrapping. A two-line Tabellenkopf is the price, and it carries the next longer heading as well, where a wider column would only have moved the collision one head along; the data cells are untouched, only `.wrap-cell` wraps there. Nothing behind the columns moves: the values, the filter, the Fortschritt, the checkboxes and the row click are untouched. It is called Findings and not Beanstandungen because the two words named one record: a second word for it cuts the chain Besuch → Finding → 5-Why/Maßnahmen in half (see the Sprachregelung below). `Nr.` is the **vergebene** `sort_order` of the row and deliberately not the row index, so it keeps its gaps after a delete (see the Vergabe pattern above); `Level` is labelled through `evalLabel(item.evaluation, true)` (the stored value stays `O`/`L1`/`L2`/`L3`), and `Frist` is the `cap_deadline` the list endpoint carries along from the CAP item. `Status` is derived just as little stored — `capStatus(cap)`, the same helper and the same `completion_date` boundary every other surface uses. A Finding without a Level has no CAP item and therefore no status, a state and not an error, so the cell stays empty. New rows are stored with `section = 'THEORETICAL'` and the section select is hidden in the dialog — the authority knows no sections, and pinning one value keeps sorting and saving untouched. A **row click drills into the Finding** (`{type:'finding'}`) instead of opening `#checklist-item-dialog`; the dialog stays the *add* path of both views. Internal plans keep the three-section view and the dialog for editing unchanged
- **Die laufende Nummer eines Findings wird vergeben, nicht abgeleitet** — Speicher ist `audit_checklist_item.sort_order`, das auf Behördenplänen bis dahin ungenutzt auf 0 stand. Beide Schreibwege liegen serverseitig: `POST /api/audit-plan-lines/:lineId/checklist-items` zählt ohne mitgeschickten Wert mit `getMaxChecklistItemSortOrder` (`COALESCE(MAX(sort_order), -1)`, also max+1 wie bei `getMaxCapActionSortOrder` und dem Zielkatalog) die **Line** weiter, und `PUT /api/checklist-items/:id` nimmt ein ausdrücklich gesendetes `sort_order` entgegen, damit der Dialog interner Audits und die beiden Importwege ihre Sortierung weiter selbst setzen. Der Bezug ist die Line und **nicht** die Sektion: die Nummer zählt über den ganzen Bericht, der ohnehin nur `THEORETICAL` kennt. Die **bewusste Folge**: nach dem Löschen von Finding 2 bleibt die Sequenz 1, 3 — genau das heißt "vergeben" statt "abgeleitet", denn eine Nummer, die sich beim Löschen eines Nachbarn ändert, ist keine, auf die ein LBA-Schreiben verweisen kann. Das ist der **Gegenentwurf** zu den drei abgeleiteten Nummern des Hauses — dem `Nr.` des Zielkatalogs, dem `Lfd.` der SRB-Tabelle und der laufenden Nummer einer `cap_action` —, die alle drei Zeilenindex bleiben und deshalb weiter lückenlos 1..n zählen. Die Lückenlosigkeit, die für sie gilt, gilt für ein Finding eines Behördenplans also ausdrücklich **nicht** mehr: sie ist dort kein Qualitätsmerkmal, sondern der Fehler. Der Unterschied ist der Adressat — eine interne Nummer wird nur in dieser App gelesen und darf sich schließen, eine Findingnummer steht in einem LBA-Schreiben und darf es nicht. `?? ` statt `||` an beiden Stellen: eine ausdrückliche `0` ist eine Nummer und keine fehlende Angabe, und ein **ausgelassenes** `sort_order` behält im PUT die gespeicherte, statt sie auf 0 zurückzusetzen — derselbe Server-Guard wie `b.authority_auditor ?? existing.authority_auditor` in `PUT /api/audit-plan-lines/:id`. **Interne Audits sind unberührt**: ihr Dialog schickt seine Sortierung seit jeher mit, ein gesendeter Wert gewinnt in beiden Routen, und die beiden Importwege (docx-Kopie in `routes/audit-plans.js`, xlsx-Sync in `routes/audit-plan-lines.js`) reichen den vorhandenen Wert unverändert durch. `tasks/smoke-checklist-sort-order.js` bootet den echten Server und deckt es ab — Vergabe 0/1/2, die Lücke nach dem Löschen, den ausdrücklichen Wert (inkl. `0`), PUT mit und ohne Feld und den internen Plan. **Oberfläche und Dokument lesen dieselbe Spalte**: `Nr.` in `renderFindingsSection()`, `findingSegmentName(item)` (Breadcrumb-Segment und `<h2>` des Finding-Screens), das Feld `Nr.` der Stammdaten und die Spalte `Nr.` der Behörden-Tabelle des Audit-Line-PDFs (`renderAuthorityFindings()` in `pdf/audit.js`) kommen aus `item.sort_order` statt aus dem Zeilenindex, und die Stammdaten zeigen sie als **reine Anzeige** (`fd-sort-order`, `readonly` in der abgedunkelten Optik, die `cap-f-root-cause` bei aktiver 5-Why trägt, und ohne die Klasse `finding-field`, die den Blur-Save auslöst). Sie war für einige Commits ein Eingabefeld und ist es **nicht mehr**: die Nummer wird serverseitig vergeben, und eine Sequenz, die zwei Wege gleichzeitig schreiben, ist genau die, auf die ein LBA-Schreiben nicht mehr verweisen kann. `sort_order` steht damit wieder in der Durchreiche-Liste von `saveFindingFields()` — neben `section` und `auditor_comment`, unverändert aus dem geladenen Datensatz, weil der PUT die ganze Zeile ersetzt; allein die Findingbericht Nr. (`document_ref`, siehe unten) bleibt dort ein bearbeitetes Feld. Weil der Name des Screens **die** Nummer ist und die sich hier nicht mehr ändern kann, benennt `renameFindingSegment(item)` das Segment nur noch beim Laden (`loadFinding()`); ein Nachziehen von `<h2>` und Breadcrumb nach dem Speichern gibt es nicht mehr. Der `+`-Button der Findingliste schlägt seither **max+1** statt `length+1` vor: nach dem Löschen von Nr. 2 steht in der Liste 1, 3, und `length+1` träfe dort auf die schon vergebene 3. Das `Nr.` des Zielkatalogs, die laufende Nummer einer `cap_action` und die `#`-Spalte interner Audits bleiben der Zeilenindex — der Gegenentwurf steht oben. **Altbestand** aus der Zeit vor der Vergabe steht auf `0` und wird beim ersten Öffnen des Berichts **einmalig durchnummeriert**: `renumberLegacyFindings()` in `public/companies.js`, aufgerufen von `loadLineData()` und nur beim Behördenplan, gibt jeder `0` in Ladereihenfolge die nächste freie Nummer und schreibt sie je Finding mit einem `PUT /api/checklist-items/:id` zurück. Es war eine Weile lang das Eingabefeld der Stammdaten, das den Altbestand von Hand geradezog; seit die Nr. dort nur noch Anzeige ist, gäbe es sonst gar keinen Weg mehr, und eine Findingliste aus lauter Nullen ist keine Nummerierung, auf die ein LBA-Schreiben verweisen könnte. Es ist trotzdem **keine Migration**: kein Schema-Schritt, kein Migrationsflag und keine Zeile im Server — dieselbe Grenze wie bei der Lese-Migration der `cap_action`-Maßnahmen, die auch im Frontend beim ersten Öffnen läuft. Die `0` ist auf einem Behördenplan das **eindeutige Kennzeichen** des Altbestands: der `+`-Button schickt seine Nummer selbst mit und zählt ab max+1 mit Untergrenze 1, ein regulär angelegtes Finding trägt also nie die `0` — die serverseitige max+1-Vergabe, die für eine leere Line bei `0` beginnt, greift nur für Aufrufer ohne Feld, und das ist keine Behörden-Oberfläche. Gezählt wird mit **derselben** Formel wie im `+`-Button (max+1 über alle geladenen `sort_order`, Untergrenze 1), damit eine nachgetragene Nummer nicht auf eine schon vergebene trifft; ein gemischter Bestand behält deshalb seine vergebenen Nummern und die `0` zählt hinten weiter, statt sich dazwischenzuschieben. Der PUT reicht den Datensatz sonst **unverändert** durch und lässt `cap_deadline` bewusst aus — ein ausgelassenes Feld lässt die am CAP-Item gepflegte Frist stehen, und die mitgereichte, unveränderte `evaluation` verhindert, dass die Route das CAP-Item abräumt. Der lokale Datensatz wird erst **nach** dem erfolgreichen Schreiben fortgeschrieben, ein Abbruch mittendrin zeigt also keine Nummer an, die nicht gespeichert ist: die bereits geschriebenen stehen, der Rest bleibt auf `0` und wird beim nächsten Laden erneut versucht — ohne verbleibende Nullen ist der Durchlauf ein No-op und damit idempotent. `tasks/smoke-legacy-finding-renumber.js` bootet den echten Server und spielt die Schleife nach: Vergabe in Ladereihenfolge, überlebendes CAP-Item samt Frist, Level und Findingbericht Nr., der No-op beim zweiten Lauf und der gemischte Bestand. **Interne Audits sind unberührt** — der Durchlauf hängt am `plan_type`, ihre Sortierung ist sektionsweise und wird vom Dialog gesetzt

The five `<label>` of `fw-why1..fw-why5` carry **exactly the box heads of the CM-002 PDF** — `1. Why is it happening? (Auswirkung)`, `2.`–`5. Why is that? (…)`, the `WHY_STEPS` strings of `pdf/five-why.js` (see its pattern above), written out a second time because the two files share no module. The five question texts of the original form sit **as an editable default value in the field**, not as a `placeholder`: `WHY_DEFAULTS` in `public/companies.js` (`Auswirkung: Was ist das aufgetretene Problem? Welche Störungen treten auf?` and its four siblings). In the real CM-002 the Bearbeiter typed those sentences into the field by hand, so the form takes exactly that off him — a placeholder would have looked the same on screen and never reached the sheet that goes to the authority. Two **deliberately accepted** consequences: a field emptied on purpose stands on its default again the next time it is opened — an empty string is indistinguishable from "never filled in" as long as there is no marker column, and that column would be the migration this case is not worth — and without any interaction **nothing** is written: a CAP without a `five_why` record stays the empty, hand-fillable CM-002, the same boundary the renderer draws. Labels and defaults land on both screens at once, which is the point of the shared markup. The record hangs off the **CAP item**, which only exists once the Finding has a Level — without one the section renders a speaking empty state instead of fields that could not be saved anywhere. `PUT /api/cap-items/:id/five-why` mirrors the Root Cause into `cap_item.root_cause`, and `onRootCause()` carries that second copy to wherever the calling screen also holds it: the read-only `Ursache` field on the CAP level, `currentFindingCap.root_cause` on the Finding. `initFiveWhy()` scopes every lookup to `#five-why-grid` and drops a late `GET` response when that grid is no longer `isConnected` — on the Finding level every Levelwechsel re-renders the screen, and the reused IDs would otherwise let an in-flight load write another CAP item's analysis into the fresh fields
- The Maßnahmen section of that screen (`#finding-actions`, `findingActionsHtml()`) is **three groups**: the `cap_action` rows of kind `CORRECTIVE` (*Behebungsmaßnahmen*), those of kind `PREVENTIVE` (*Präventivmaßnahmen*), each a table with its own `+` button, and *Erledigung des Findings* — Verantwortlicher (`responsible_person`), Erledigt am (`completion_date`) and the Status, the three fields that hang on the `cap_item` itself. The two lists carry the Mehrzahl the LBA writes into a CAP, the third group is what closes the finding as a whole; it has a heading of its own because `responsible_person` and `completion_date` exist a second time **per row** above it and would otherwise read as one more column of the Präventivmaßnahmen. `CAP_ACTION_GROUPS` in `public/companies.js` is the one place the two kinds, their labels and their legacy column are written down — list, `+` button and read migration would otherwise drift. The **laufende Nr. is derived from the row index within its own group** and never stored, like the `Nr.` of the Zielkatalog and unlike the `Nr.` of the Finding above it, so it stays gapless 1..n when a Maßnahme is deleted; the rows carry no IDs but classes plus `data-cap-action`, because there are n of them. Everything **auto-saves on blur**: a row through `saveCapAction()` (`PUT /api/cap-actions/:id`, partial — `kind` and `sort_order` keep their value, and an emptied date really clears to NULL, since unlike the Frist it lives on this one screen only), the third group through `saveFindingCapFields()`. Nothing is redrawn on a save — the local record is written in place, so the focus of the field the user just tabbed into survives; `saveCapAction()` even assigns the local copy **before** the response, because the blur a `+` click triggers races the re-render of that list. Only `+` and delete redraw, and only the **one** list they touch (`renderCapActionList(kind)` + `wireCapActionRows(kind)`), which is also what renumbers the group. The **Status is derived, never stored**: `capStatus(cap)` reads `completion_date` and is the one place that boundary is written down (`renderCapItemsLevel()` dropped its own nested copy), so the badge is patched in place after a save. `PUT /api/cap-items/:id` **replaces** the whole row, so `deadline`, `root_cause`, `evidence` **and the two legacy Maßnahmentexte** travel unchanged from `currentFindingCap` — the Frist is edited in the Stammdaten, the Ursache is mirrored in by the 5-Why (`onRootCause()` keeps that copy current), the Nachweis-Text this screen does not show at all, and `corrective_action` / `preventive_action` are the CM-003 fallback that this screen must not clear; without them every save here would silently wipe all five. For the same reason `saveFindingFields()` writes a changed Frist back into `currentFindingCap.deadline`: the next Maßnahmen-Save would otherwise restore the Frist from before. The Frist is deliberately **not** shown a second time in this section — one column (`cap_item.deadline`) on two screens means one of them is stale after every save; `cap_action.target_date` is a Zieldatum of a single Maßnahme and never the Frist of the Finding. Without a Level there is no CAP item and the section renders the same speaking empty state as the Ursachenanalyse
- **Altbestand kommt beim ersten Öffnen als je EINE Maßnahme herein.** `loadFindingActions(cap)` reads `GET /api/cap-items/:id/actions`, and if that list is **empty** while `corrective_action` / `preventive_action` still carry text, it posts each of the two as one `cap_action` of its kind — a read migration in the frontend, no server-side backfill and no migration flag. The two columns stay exactly where they are: they are the CM-003 fallback for everything that never passes this screen, and the PDF prints them only while there are no `cap_action` rows, so nothing is printed twice. The empty list is therefore the **right** trigger and not a missing marker column: as long as it is empty, those two texts *are* the Maßnahmen of the Finding, because they are precisely what gets printed — a screen showing "keine Maßnahmen" next to a CM-003 printing two would contradict its own document. Deleting every row of a legacy CAP consequently re-materializes them on the next open, which is that same consistency and not a bug
- **`cap_action` — die Mehrzahl der Maßnahmen ist die einzige echte Modell-Lücke des Behördenaudits.** Von den vier Sätzen, die ein Behördenaudit ausmachen — ein Besuch am Datum, dazu seine Findings, je Finding eine 5-Why-Analyse, je Finding **mehrere** durchnummerierte Behebungs- und Präventivmaßnahmen — bildet das bestehende Modell drei korrekt ab: der Besuch ist der `audit_plan` mit seinem einen `audit_plan_line`, das Finding ist genau ein `audit_checklist_item`, die 5-Why ist der `five_why`-Satz am CAP-Item. Nur die vierte fehlte: `cap_item` trägt je EIN Textfeld `corrective_action` / `preventive_action`. Deshalb **eine additive Tabelle** statt fünf neuer Behörden-Tabellen samt Datenmigration — `cap_action` hängt per `ON DELETE CASCADE` am CAP-Item, `corrective_action` / `preventive_action` bleiben als Altbestand und CM-003-Fallback stehen, es gibt weder Drop noch Migration. Der Gewinn ist genau das, was **nicht** angefasst wird: Home-Dashboard, Fristen-Mails (`services/notifications.js`), Papierkorb-Snapshot und jede Deadline-Statistik lesen weiter exakt die `cap_item`-Zeilen, die sie heute lesen; fünf Behörden-Tabellen hätten jede dieser Leserstellen ein zweites Mal geschrieben. Der **Preis** dieser Variante, ausdrücklich benannt und nicht nachträglich zu bedauern: die Stufe bleibt die `evaluation` des `audit_checklist_item` mit den intern gespeicherten Werten `O` / `L1` / `L2` / `L3` und Klartext nur in der Beschriftung (`evalLabel()` / `capEvalLabel()` / `authorityEvalLabel()`) statt einer eigenen `level`-Spalte, und der Unterzeichner des CM-002 kommt weiter aus `getQmForDepartment()` statt aus einer eigenen Unterschriftsspalte am `five_why` — beides wäre die Migration, die der Fall nicht wert ist
- Die Regeln dieser Tabelle: `kind` (`CORRECTIVE` | `PREVENTIVE`) trennt die beiden Gruppen und `sort_order` ist die Reihenfolge **innerhalb** einer Gruppe — beide Gruppen haben ihre eigene, bei 0 beginnende Zählung, weshalb `getMaxCapActionSortOrder` auf `cap_item_id` **und** `kind` filtert und für eine leere Gruppe `-1` liefert, damit der Aufrufer wie beim Zielkatalog mit max+1 rechnet. Die gedruckte laufende Nummer ist **abgeleitet und nie gespeichert**: sie ist der Index in der nach `kind, sort_order, created_at` sortierten Liste (`getCapActionsByCapItem`), genau wie das `Nr.` des Zielkatalogs — und ausdrücklich **anders** als das `Nr.` der flachen Findingliste, das vergeben ist: eine interne Maßnahmennummer darf sich beim Löschen einer Nachbarzeile schließen, die Nummer eines Findings nicht, weil ein LBA-Schreiben auf sie verweist. So bleibt sie beim Löschen einer Maßnahme lückenlos 1..n. Die **Frist bleibt am Finding** (`cap_item.deadline`): sie ist die Frist, welche die Behörde gesetzt hat, und die Fristen-Mails und das Home-Dashboard lesen genau diese eine Spalte; `cap_action.target_date` ist ausschließlich ein internes Zwischenziel einer einzelnen Maßnahme und darf nirgends als Frist des Findings auftreten. Das CM-003 hat für die Maßnahmen **eine** Formularzelle je Art, also joint `capActionCell()` in `pdf/cap.js` die Maßnahmen einer Gruppe als `1. … 2. …` in diese eine Zelle; ohne `cap_action`-Zeilen fällt es auf `cap.corrective_action` / `cap.preventive_action` zurück — was jedes vor der Tabelle angelegte CAP-Item unverändert weiterdruckt und genau der Grund ist, warum die beiden Spalten bleiben. Ausschlaggebend ist die **leere Liste, nicht der leere Text**: sobald Zeilen da sind, sind sie die Maßnahmen des Findings, dieselbe Grenze, an der auch die Lese-Migration des Screens hängt — eine Zeile ohne Beschreibung hat nichts zu drucken und zählt deshalb bei der Nummerierung nicht mit, damit die Zelle lückenlos 1..n bleibt. Geladen werden die Zeilen wie der 5-Why-Satz **vom Aufrufer** (`generateCapItemsPdfBuffer` plus Einzel- und Batch-Route in `routes/cap-items.js`) und dem Renderer übergeben, nicht im Renderer gelesen; `responsible_person` und `completion_date` einer einzelnen Maßnahme bleiben außen vor, weil das Formular dafür keine Spalte hat — gedruckt wird der Verantwortliche des CAP-Items. Im **Papierkorb** hängen die Maßnahmen an derselben CASCADE wie `cap_evidence_file` und `five_why` und werden deshalb genauso mitgesichert: `snapshotCapItem()` (`services/trash.js`) legt sie als `cap_actions` neben `evidence_files` und `five_why`, und `restoreCapItem()` schreibt sie über `stmts.restoreCapAction` mit den **Original-UUIDs und den Original-Zeitstempeln** in derselben Transaktion zurück, in der auch das CAP-Item entsteht — `sort_order` und `created_at` **sind** die Sortierung, aus der die laufende Nummer abgeleitet wird, ein frischer Zeitstempel würde sie beim Wiederherstellen umsortieren. Weil jeder darüberliegende Snapshot (Prüfpunkt, Audit-Line, Auditplan) durch dieselbe Funktion geht — `snapshotAuditPlanLine()` ruft seither `snapshotCapItem()` auf, statt dessen Kinderliste ein zweites Mal einzurücken — steht die Liste der CAP-Kinder an genau EINER Stelle; die eingerückte Kopie war die Stelle, die beim nächsten Kind wieder vergessen worden wäre. Ein Snapshot von **vor** der Tabelle hat das Feld schlicht nicht: das ist kein Fehler, sondern ein CAP ohne Maßnahmenliste, wird mit Default auf die leere Liste gelesen und ausdrücklich **nicht** aus `corrective_action` / `preventive_action` nachgebildet — die beiden Textfelder stehen in derselben wiederhergestellten Zeile ohnehin noch drin und sind der CM-003-Fallback, aus dem sie gedruckt werden

Reason: the original CM-006 forms contradict each other (`-2` and `Nicht erfüllt` in the same column, `Erfüllt` + `Positiv` at SPT 20 / SPI 0), so every automatic rule would print something the Safety Manager did not decide

## Accessibility

- Dialogs use `aria-labelledby` pointing to their heading element
- Tab bars use `role="tablist"` / `role="tab"` / `role="tabpanel"` with `aria-selected` toggled dynamically
- Visually-hidden labels use `.sr-only` CSS utility class (e.g., login password label)
- Icon-only nav buttons have `aria-label` for screen readers
- Global `:focus-visible` outline (2px solid primary); bare `outline: none` replaced with `:focus:not(:focus-visible)` pattern
- Touch targets: minimum 44×44px on interactive elements (tab buttons, icon buttons, reorder handles)
- Toast accessibility: container has `aria-live="polite"`, error toasts use `role="alert"` and persist with close button, success toasts use `role="status"`
- `@media (prefers-reduced-motion: reduce)` disables toast-in animation, share-blink animation, progress bar transitions, and the inline `.spinner` rotation
- Clickable table rows: use `makeRowClickable(row, handler)` from `app.js` — sets `role="button"`, `tabindex="0"`, and a keydown handler that fires the click on Enter/Space (used by audit lines, change rows, home CAP rows)
- Icon-only buttons: wrap bare clickable `<svg>` in `<button type="button" class="icon-btn" aria-label="…">` (44×44 min touch target). The PDF-share buttons in audit/CAP table headers use `.select-share-btn` on top of `.icon-btn`
- Skip link: `<a href="#main" class="skip-link">` is the first child of `<body>`; off-screen by default, slides into view on `:focus`. The page wraps `<%- body %>` in `<main id="main">`
- Color contrast: `.eval-O` uses `#78350f` on `#fde68a` (≥4.5:1 ratio) — earlier `#713f12` was too low
- Inline progress feedback: long-running ops (backup, deadline recalc, email send, imports) swap the button label for `<span class="spinner" aria-hidden="true"></span>…` while disabled
- Native date hints: text-based `TT.MM.JJJJ` inputs in `views/change.ejs` carry `pattern="\d{2}\.\d{2}\.\d{4}"`, `inputmode="numeric"`, `title="TT.MM.JJJJ"` so the browser surfaces format errors immediately

## Database Tables

company, department, audit_plan, audit_plan_line, audit_checklist_item, checklist_evidence_file, cap_item, cap_action, cap_evidence_file, five_why, person, app_setting, audit_log, trash_item, change_request, change_task, risk_analysis, risk_analysis_history, risk_item, safety_year, sms_meeting, safety_objective, spi_evaluation

`safety_objective` and `spi_evaluation` are back in `schema.sql` in CM-006 form —
scoped to the safety year, not the department. The department-scoped predecessors
had been dead code since the CM-025 rework (no route, no prepared statement read
them), so a **pre-schema** block at the top of `runMigrations()` drops the pair
whenever `safety_objective` lacks `safety_year_id`; nothing is carried over.
The drop has to run before `db.exec(schema)` because `CREATE TABLE IF NOT EXISTS`
leaves an existing table untouched — it would never reshape the legacy pair.
`routes/trash.js` has a restore helper for every AC-SMS type, so it no longer
keeps an obsolete-type list. Snapshots of the *predecessors* that may still sit
in `trash_item` are told apart by **shape** instead: neither the old
`safety_objective` nor the old `spi_evaluation` knew `safety_year_id`, so a
snapshot without that field is rejected with 409 and only the CM-006 rows
restore. A `safety_objective` snapshot carries its evaluations and a
`safety_year` snapshot its whole catalogue, because both cascade on delete.
Deleting a single evaluation snapshots it on its own (parent
`safety_objective`) — `snapshotSpiEvaluation()` reads the **raw** row, since the
`COALESCE` columns of `getSpiEvaluation` would hand an unsigned draft the
current catalogue as its snapshot and freeze a document nobody signed.
Restore writes the three `*_snapshot` columns back verbatim and never re-derives
them from the catalogue, so `restoreSpiEvaluation()` guards them with
`=== undefined` instead of `||`: an empty `spt_snapshot` is a valid freeze (`spt`
is optional in the catalogue), and collapsing it to NULL would let the `COALESCE`
of `getSpiEvaluation` print today's target on a document signed without one.
Only a snapshot predating those columns yields `undefined` — which better-sqlite3
rejects as a binding, hence the explicit NULL.

## Email Routing

- AC-Audit emails use `smtp_*` settings (from: ac-audit@...), title: "Compliance Monitoring Manager"
- AC-Change emails use `change_smtp_*` settings (from: ac-change@...), title: "Safety Manager"
- AC-SMS emails (SRB protocol, SPI evaluations, SPI year package) ride the **AC-Change** route: module `'change'`, so the same `change_smtp_*` settings and the same "Safety Manager" signature. All three build subject and body through `safetyMail()` in `routes/safety.js` — the formal and the informal variant differ only in salutation and closing, so the caller passes just the noun phrase (`document`) that appears in both
- All outgoing emails set `replyTo` to the QM email of the department
- Settings split into tabs: Global (backup), AC-Audit (CAP, notifications, SMTP), AC-Change (SMTP), AC-SMS (SRB-Standard-Themen)
